# 渲染与分页：1794 条怎么做到不卡

> 目标：切视图 2–8ms，点选 1ms，首屏 1.7s。

---

## 问题

不分页、每次切筛选都重建整页 DOM 时，1794 条卡片会让切视图卡到 1 秒以上；点一个卡片也要等页面重排。

## 三个改动

### 一 · 100 条/页 + 前端切分

- `PAGE_SIZE = 100`，底部加上/下一页与页码
- 数据一次取回，分页只改渲染范围，不再发请求
- 为什么是 100：50 条一页翻页太频繁；250 条一页首屏就慢了。100 是「翻页次数」和「首屏时间」的交点

### 二 · 点选只切样式，不重建

- 旧做法：点选后重新渲染整个列表
- 新做法：只改该卡片的 `selected` 类
- 效果：点选 1.0ms（原来有明显延迟感）

### 三 · 归档视图改为一次取全，前端过滤

- 旧做法：每切一次视图就发一次 `/api/items?archive=...`
- 新做法：一次取 `archive=all`，切换时在前端 filter
- 效果：切视图 2–8ms，且切换不再依赖网络

## 实测

| 操作 | 耗时 |
|---|---|
| 首屏（100 卡） | 1.72–1.77 s |
| 切视图 | 2–8 ms |
| 点选 | 0.9–1.0 ms |
| 全选本页 | 7.4 ms |
| 排序（正/倒序） | 6–8 ms |
| 类目筛选 | 7–8 ms |
| 月份筛选（双口径） | 6–12 ms |

## 顺带解决的排序口径

现象：库内条数与列表顺序对不上。

根因：最早用 `aweme_id` 排序，而 id 是雪花号，**不代表收藏顺序**（实测按 id 倒序取前 20，只有 9 条与平台一致）。

定案：新增 `fav_item.fav_seq`，完整重扫时按列表实际顺序重排（越大越新），增量只接新值，重扫后未再出现的条目置空并沉底。实测采集前 20 条与库内按序号倒序前 20 条 **20/20 一致**。

## 一个取舍

分页让「全局全选」变成「全选本页」。跨页选择用集合保留——代价是用户要自己知道选了几页，界面上用「已选 N 条」明示。
