# 为什么用「归档」代替「取消收藏」

> 一句话：不把不可逆操作交给一个本地小工具。

---

## 问题

初版设计里有「取消收藏」——勾选若干条，一键从平台收藏夹移除。

## 为什么砍掉

1. **不可逆。** 取消收藏没有回收站，误触一次就是永久丢失；而收藏夹里恰恰有很多「当时没时间看、以后要看」的东西，一次批量误操作全没了。
2. **写操作的失败模式不可控。** 读接口失败了可以重试；写接口失败了状态未知——到底删了没删，本地和平台可能不一致，需要额外的对账逻辑。
3. **和「让收藏夹不再吃灰」的初衷冲突。** 这个工具的目的是筛出值得看的内容，不是清空收藏夹。

## 定案

- 删除前端按钮与对应端点，代码内保留注释说明缘由
- 改成**本地归档**：新增 `fav_item.archived` 列（自动迁移），`POST /api/archive` 只改本地标记
- 顶栏三视图：**未归档 / 已归档 / 全部**，按钮随视图切换为「取消归档」
- 撤销零成本：再点一次就回来

## 效果

- 归档 3 条：主列表 1791 → 1788，已归档视图 3 条，撤销后复原
- 用户获得「眼不见为净」的整理感，而平台数据完全没动

## 通用原则

本地工具处理**别人的数据**时，默认只做读和本地标记；任何跨系统、不可逆的写操作，要么不做，要么加确认 + 可回滚。这条原则后来也用在了「消失检测」上——只提示，不自动删。
