# 增量同步设计

> 目标：把「每次全扫 3 分钟」降到「没变化时 24 秒」。

---

## 问题

完整扫描要滚过整个收藏列表，1791 条约 3 分钟。但绝大多数时间收藏是没变的——为了确认「没变」付 3 分钟，体验上等于没有更新按钮。

## 试过的方案

**方案 A：比时间戳。** 只抓最新的，遇到比库内最新还旧的就停。
- 失败：收藏顺序会变（取消再收藏、平台重排），时间戳不可靠；而且漏掉的旧条目永远不会被发现。

**方案 B：比总数。** 先取第一页总数，与库内比对，相同就跳过。
- 失败：总数相同不等于内容相同（删一条加一条，总数不变）。

**方案 C：已知 id 集合 + 连续 8 批无新增**（定案）
- 采集前从 `fav_item` 取 `status=active` 的全部 id 作为 `known_ids`
- 每批数据只要**有一条不在** `known_ids` 里，就继续往下滚
- **连续 8 批全部是老条目，判定「已追平」，提前结束**

## 为什么是 8 批

- 1–3 批：太激进，列表头部有少量重排时会误判追平，漏掉真正的新条目
- 8 批：按每批约 20 条算，等于「连续 160 条都是见过的」，误判概率足够低
- 再往上：收益递减，白等

这个值是实测调的，不是拍的。

## 效果

| 场景 | 耗时 |
|---|---|
| 无变化（追平即停） | 24 s（其中 14 s 是启动浏览器） |
| 只有 25 条新内容 | 15.3 s |
| 完整重扫 | 约 3 分钟 / 1779 条 |

## 代价

**消失检测被降级。** 增量模式只滚到追平就停，扫不到列表尾部，因此无法判断「某条是不是被取消收藏了」。

处理方式：只在**完整重扫且没有撞上限**的那次，统计「本次未出现」的条目数，在状态栏提示「另有 N 条本次未出现」——提示，不自动删。

## 另一个坑：数量上限

「全部」并不等于无限。加了 `MAX_SCAN = 3000` 作为单次扫描的安全上限，防止收藏异常增长或分页失控时把内存吃爆。撞到上限时状态会明确标注，避免「以为扫完了其实没扫完」。
